Arquitectura de LinkedIn Tutor AI

Una aplicación Blazor Web App en modo Interactive Server que actúa como tutor de LinkedIn, consumiendo un agente ya existente en Azure AI Foundry. Diseño en Clean Architecture, autenticación dual y soporte de chat con y sin streaming.

01Estructura de carpetas

Solución Clean Architecture de cuatro capas, con src/ para el código de producción y tests/ espejando la estructura. La regla de dependencias es estricta y unidireccional: Domain ← Application ← Infrastructure ← Web.

Convención de命名Los proyectos conservan el prefijo LinkedInTutorAI para evitar colisiones de namespaces y facilitar el despliegue con un solo ensamblado raíz. Web es el único proyecto con Microsoft.NET.Sdk.Web.

03Interfaces

Los contratos viven en Application y Domain. Web y Infrastructure programan contra abstracciones, nunca contra implementaciones concretas.

Domain

ITutorSessionRepository
Persistencia de sesiones y mensajes: GetByIdAsync, GetByUserAsync, SaveAsync, AddMessageAsync.
IAggregateRoot
Marker para raíces de agregado (opcional, para orden académico).

Application

IAiFoundryAgentService
Contrato del agente. AskAsync(request, ct) → ChatResponseDto y AskStreamAsync(request, ct) → IAsyncEnumerable<ChatStreamChunkDto>.
IChatOrchestrator
Caso de uso central. HandleUserMessageAsync y HandleUserMessageStreamAsync: valida, carga sesión, llama al agente, persiste, mapea.
ITutorSessionService
Ciclo de vida de sesión: crear, cargar historial, listar.
IOptions<TutorOptions>
Acceso tipado y validado a la configuración del agente.

Por qué el contrato del agente está en ApplicationSi pusieras IAiFoundryAgentService en Infrastructure, Application no podría referenciarlo sin invertir la flecha de dependencia. Al declararlo en Application e implementarlo en Infrastructure se resperta la inversión de dependencias (DIP).

04Servicios

Una implementación por contrato, con responsabilidades finas. El orquestador es el único que conoce el flujo completo; el servicio de Azure solo habla con Foundry.

Infrastructure · AiFoundry

AgentsAiFoundryAgentService

Implementa IAiFoundryAgentService. Recupera el agente existente por AgentId, crea/abre un thread, añade el mensaje del usuario, lanza el run y expone los eventos de streaming como IAsyncEnumerable.

Infrastructure · AiFoundry

AiFoundryCredentialFactory

Devuelve DefaultAzureCredential o AzureKeyCredential según TutorOptions.AuthMode. Único punto que decide cómo autenticarse.

Infrastructure · AiFoundry

AgentMessageMapper

Traduce entre los modelos del SDK de Azure (AgentMessage, RunStreamEvent) y los DTOs de Application. Aísla a la app de la forma del SDK.

Infrastructure · Persistence

InMemoryTutorSessionRepository

Persistencia académica por circuito. Sustituible por EF Core + SQLite sin tocar Application.

Application

ChatOrchestrator

Valida la entrada, carga/crea la sesión, persiste el mensaje del usuario, invoca al agente, persiste la respuesta del asistente y mapea. Propaga CancellationToken en todo el camino.

Application

TutorSessionService

CRUD de sesiones contra el repositorio. Expone historial paginado a la UI.

Web · State

TutorChatState

Estado del componente Blazor: lista de mensajes, IsStreaming, error actual. Llama al orquestador y dispara StateHasChanged por cada chunk.

Web · Endpoints

ChatEndpoints

Minimal API opcional (POST /api/chat) para exponer el tutor también como REST, no solo Blazor.

05DTOs

Todos los DTOs viven en Application/Dtos. Son la única forma de datos que cruza hacia Web; los modelos del SDK de Azure nunca llegan a la UI.

DTOCampos claveUso
ChatRequestDtoSessionId, UserMessage, LinkedInProfileEntrada del usuario + contexto de perfil para personalizar la tutoría.
ChatResponseDtoSessionId, MessageId, AssistantMessage, FinishReason, CreatedAtRespuesta completa (modo no-streaming).
ChatStreamChunkDtoDelta, IsFinal, MessageId, SessionIdToken incremental para streaming; IsFinal cierra el stream.
SessionDtoId, UserId, Title, CreatedAt, Messages[]Vista de una sesión con su historial.
MessageDtoId, Role (User/Assistant), Content, CreatedAtMensaje individual dentro del historial.
LinkedInProfileDtoHeadline, Industry, ExperienceYears, GoalsContexto de LinkedIn que enriquece el prompt del tutor.
ErrorDtoCode, Message, Details, TraceIdRepresentación segura de error para la UI (sin secretos ni stack traces).
TutorOptionsEndpoint, ProjectConnectionString, AgentId, ModelDeployment, AuthMode, ApiKey, MaxRetries, TimeoutSecondsPOCO de configuración tipada y validada con IOptions<T>.

Perfil de LinkedIn como contextoEl LinkedInProfileDto no se guarda del lado del agente necesariamente; se inyecta como contexto en cada mensaje para que el tutor responda acorde al perfil y objetivos del usuario.

06Flujo de llamadas

El modo streaming es el camino principal y el que más aprovecha el modelo server-side: los tokens viajan por IAsyncEnumerable sobre el circuito SignalR de Blazor y se renderizan token a token. El modo no-streaming sigue el mismo camino pero devuelve un ChatResponseDto completo al finalizar.

sequenceDiagram
  autonumber
  participant U as Usuario
  participant UI as TutorChat.razor
  participant S as TutorChatState
  participant O as ChatOrchestrator
  participant A as AgentsAiFoundryService
  participant R as SessionRepository
  participant F as Azure AI Foundry (agente)
  U->>UI: escribe mensaje
  UI->>S: SendAsync(text)
  S->>O: HandleUserMessageStreamAsync(sessionId, text, ct)
  O->>R: cargar sesión + persistir msg User
  O->>A: AskStreamAsync(ChatRequestDto, ct)
  A->>F: abrir thread + añadir mensaje + run(agentId)
  loop streaming de eventos
    F-->>A: RunStreamEvent (delta token)
    A-->>O: ChatStreamChunkDto
    O-->>S: chunk vía IAsyncEnumerable
    S-->>UI: StateHasChanged (token a token)
  end
  O->>R: persistir msg Assistant (ensamblado)
  O-->>S: stream completado
  S-->>UI: fin · IsStreaming=false

Puntos de cancelación

  • El CancellationToken nace en el evento de UI (clic en “Detener”) y se propaga: State → Orchestrator → AgentService → run de Foundry.
  • Al cancelar, el orquestador detiene la enumeración y marca el último chunk parcial como no-final; la sesión conserva el mensaje del usuario para reintentar.
  • El circuito Blazor cerrado por el navegador cancela automáticamente el stream (SignalR libera el cts).

07Manejo de errores

Estrategia por capas: las excepciones de dominio son semánticas, las del SDK de Azure se traducen en la frontera de Infrastructure, y Web solo recibe ErrorDto en español, sin secretos ni trazas técnicas.

Mapa de traducción de errores

OrigenHTTP / condiciónExcepción de ApplicationSeveridadMensaje al usuario
Validaciónmensaje vacío / > 4000 charsValidationExceptionvalidación“Escribe un mensaje válido para continuar.”
Azure401 / 403AiFoundryAuthExceptioncrítico“No se pudo autenticar con el tutor. Revisa la configuración.”
Azure408 / 504AiFoundryTimeoutExceptionaviso“El tutor tardó demasiado. Intenta de nuevo.”
Azure429AiFoundryThrottledExceptionaviso“Demasiadas solicitudes. Espera unos segundos.”
Azure5xxAiFoundryUnavailableExceptionaviso“El tutor no está disponible ahora. Intenta más tarde.”
Dom.sesión inexistenteSessionNotFoundExceptionaviso“No se encontró la sesión. Se creó una nueva.”

Mecanismos

  • Resiliencia (Polly): retry con backoff exponencial + jitter para 429/5xx, circuit breaker tras N fallos consecutivos, timeout por llamada. Configurable en TutorOptions.
  • Cancelación: CancellationToken en toda la cadena; el circuito caído cancela el run de Foundry.
  • Boundaries: Infrastructure captura Azure.RequestFailedException y la traduce. Web nunca ve tipos de Azure.
  • UI Blazor: <ErrorBoundary> envolviendo el chat; estado de error en TutorChatState para mensajes en línea.
  • Falla global: app.UseExceptionHandler("/Error") y página Error.razor ya migradas.
  • Observabilidad: ILogger con TraceId por sesión para correlacionar fallos (correlación de errores).

08Configuración

Configuración tipada y validada con IOptions<TutorOptions> + ValidateOnStart: la app falla al arrancar si falta AgentId o Endpoint, en lugar de romper al primer mensaje. AuthMode alterna la credencial en runtime.

{
  "AiFoundry": {
    "Endpoint": "https://<foundry>.services.ai.azure.com/api/projects/<project>",
    "AgentId": "asst_xxxxxxxxxxxxxxxxxxxx",
    "ModelDeployment": "gpt-4o-mini",
    "AuthMode": "DefaultCredential",
    "MaxRetries": 3,
    "TimeoutSeconds": 60
  },
  "Logging": { "LogLevel": { "Default": "Information" } },
  "AllowedHosts": "*"
}

Gestión de secretos por entorno

Development
ApiKey vía User Secrets (dotnet user-secrets). Nunca en appsettings.Development.json.
Production
ApiKey vía Azure Key Vault o variables de entorno. AuthMode=DefaultCredential + Managed Identity recomendado.
Switch
AuthMode = DefaultCredential | ApiKey. ApiKey solo se lee si el modo es ApiKey.

Validación al inicioCon services.AddOptions<TutorOptions>().Bind(config).ValidateDataAnnotations().ValidateOnStart(), una configuración incompleta lanza OptionsValidationException durante Program.cs: detección temprana, no error silencioso en producción.

10Justificación técnica

Cada decisión, con su porqué y la alternativa descartada.

Decisión

Clean Architecture en 4 proyectos

Por qué: aísla reglas de negocio del SDK de Azure y de la UI; testeable sin red; cambiar de proveedor de IA toca solo Infrastructure. Alternativa: proyecto único con carpetas — más rápido pero sin separación formal, débil para un trabajo académico evaluado.

Decisión

Azure.AI.Agents (no el SDK de Inferencia)

Por qué: el SDK de Agentes es el oficial para consumir agentes de Foundry: threads, runs y streaming de eventos. El SDK de Inferencia solo chat con modelos sueltos, sin agente. Alternativa: HTTP plano a la API de agentes — pierde tipado, reintentos y manejo de streaming.

Decisión

Consumir agente existente por ID

Por qué: el agente ya está definido en Foundry (prompt, herramientas, modelo). El código no lo crea: lo recupera con AgentId y ejecuta runs. Single source of governance: el agente se actualiza en Foundry sin redeploy de la app.

Decisión

Auth dual conmutable por config

Por qué: DefaultAzureCredential es best practice (sin secretos), pero el modo académico/local puede no tener Managed Identity; ApiKey da un escape hatch. La CredentialFactory decide en runtime. Alternativa: solo uno — o fricción local, o secreto en producción.

Decisión

Blazor Interactive Server

Por qué: cumple “todo corre en el servidor”; el streaming por IAsyncEnumerable sobre SignalR es natural server-side y da experiencia tipo ChatGPT sin WebAssembly. Alternativa: Blazor WebAssembly — ejecución en cliente, no cumple el requisito.

Decisión

Streaming + no-streaming

Por qué: streaming para UX en vivo; no-streaming para integraciones REST y tests deterministas. Dos métodos del mismo servicio, mismo orquestador. Alternativa: solo streaming — difícil de testear y consumir vía API.

Decisión

DTOs en Application, mapeo en el boundary

Por qué: la UI y los tests no conocen los tipos de Azure; cambios de versión del SDK no rompen contratos. Alternativa: exponer modelos del SDK — acoplamiento total.

Decisión

Polly / Http Resilience

Por qué: los endpoints de LLM devuelven 429 y 5xx con frecuencia; retry + circuit breaker + timeout son estándar. Alternativa: sin resiliencia — fallos en cascada ante picos.

Decisión

IOptions + ValidateOnStart

Por qué: fail-fast: si falta AgentId o Endpoint, la app no arranca con un error claro, no falla en el primer mensaje. Alternativa: leer config con strings sueltos — errores tardíos y difíciles de rastrear.

Decisión

Traducción de errores en la frontera

Por qué: Web nunca ve Azure.RequestFailedException; recibe ErrorDto con mensaje en español y TraceId. Alternativa: propagar excepciones del SDK — filtración de secretos y trazas al cliente.
